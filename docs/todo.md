## 1. エンティティ定義

### 1.1 User（エンドユーザー）

- [x] 同一 Discord ユーザーが複数サーバーで認証した場合の検索範囲 → 組織単位。組織内ではサーバー横断で Discord ID 検索できる。組織をまたぐ横断は sysadmin のみ（03 §2.4, 05 §6.2）
- [ ] ユーザーのブロック/BAN 機能の有無。特定 Discord ID をサーバー単位・組織単位・システム全体で認証拒否する仕組みは必要か？（現設計にはない）
- [x] データ削除リクエスト（忘れられる権利）→ 組織による Discord ID 指定の削除（L-03）、本人からの依頼は sysadmin が対応。永久保存は廃止し、詳細個人データは保存期間後に消去（06 §5）

### 1.2 SystemUser（システムユーザー）

- [x] 「作成」と「所属」の違い → 作成（所有）できる組織は 1 人 1 つ、所属は複数可（01 §6）
- [x] アカウント削除 → A-04。owner は移譲または組織削除が済むまで削除できない。削除時は `system_users` を匿名化（05 §6.2, 06 §5）
- [ ] アカウント復旧手段。Discord / Microsoft のどちらでもログインできるが、複数プロバイダーの紐付け（account linking）を許可するかは未定（05 §4.1）
- [x] プロフィール情報 → Better Auth の `user`（表示名・メールアドレス・アバター）。画面は `/account`（02 §1.3）

### 1.3 Server（サーバー）

- [x] 同一 Guild ID の重複登録 → 有効なサーバー間で一意（D6, 04）
- [x] 無効化と削除の区別 → `status`: draft / active / disabled / suspended、削除は論理削除。active 以外は認証フローが `unavailable` を返す（04, 05 §10.1）
- [x] サーバー削除後の開始 URL へのアクセス → `unavailable` の結果画面（05 §10.1）。ログは 30 日後に物理削除（06 §5）
- [x] Bot の追放・退出の検知 → 参加状態チェック（S-06）。手動チェックに加え、認証時のロール付与失敗を `last_check_error` に記録（04, 05 §10.3）
- [x] 登録後に変更できる項目 → 名前・認証設定・Role ID は PATCH、Client Secret・Bot Token は別操作でローテーション（S-02, S-03, 03 §2.2）

### 1.4 Organization（組織）

- [x] 組織の削除 → 配下のサーバーを論理削除し、30 日後にログを物理削除（06 §5）。実行できるのは owner のみ（05 §6.2）
- [x] オーナー移譲と owner の退会 → 移譲は `auth.member` を同一トランザクションで更新。owner は移譲か組織削除が済むまで退会できない（05 §6.1, §6.2）
- [ ] 組織名の一意性制約・命名ルール（文字数制限、使用可能文字）
- [x] 組織のプロフィール情報 → MVP は組織名のみ（アイコン・説明文は持たない。02 §1.3）

### 1.5 Log（ログ）

- [x] ログのスキーマ → 04 `app.verification_logs`
- [x] フィンガープリントの保存形式 → 合成ハッシュ + 生の値 3 項目（D3）
- [x] サーバー削除後のログ → 孤立させず、論理削除から 30 日後に物理削除（06 §5）
- [x] ログの更新 → 追記のみ。保存期間を過ぎると詳細個人データを NULL にする以外は変更しない（04, 06 §5）
- [x] 重複認証 → 全件記録する。途中で失敗した試行（captcha・vpn 等）も残す。`expired` / `rate_limited` は残さない（05 §10.3）

## 2. RBAC（ロールベースアクセス制御）

- [x] パーミッションマトリクス（05 §6.2）
- [x] owner 不在時 → 不在の状態を作らない。owner は移譲か組織削除が済むまで退会できない（05 §6.2）
- [x] ロールの変更 → owner は全員、admin は viewer ↔ admin（自分自身は不可）。admin の招待は owner だけ（D9, 05 §6.2）
- [x] メンバーの除外 → admin は viewer のみ、owner は owner 以外（05 §6.2）
- [x] システム管理者 → Loggify 運営者。`app.sysadmins` に登録した `system_user_id`。閲覧は監査ログに記録（D7, 05 §7）

## 3. 認証・セッション管理

### 3.1 システムユーザー認証

- [x] ログイン方法 → Discord と Microsoft(Entra ID)。Passkey はログイン後の追加登録のみで、単体ログイン・新規登録は不可（05 §4.1）
- [x] Passkey の登録フロー → `/account` から登録（A-02, 02 §1.3）
- [ ] 同時ログインセッション数の制限（Better Auth の既定のまま。制限を設けるかは未定）
- [x] ログアウト・全端末ログアウト → A-03、Better Auth 標準 API（05 §5.1）

### 3.2 セッションと JWT

- [x] セッション方式 → Better Auth の DB セッション + Cookie。FastAPI には Better Auth の JWT プラグインで都度発行した短命 JWT（有効期限 30 秒）を渡す。Refresh Token は使わない（05 §3, §5.1）
- [x] revocation → DB セッションを Better Auth が管理。JWT は 30 秒で失効し、キャッシュしない（05 §3.2）
- [x] JWT の claim → `sub` / `org_id` / `role` / `exp` / `iss` / `aud`（D13, 05 §3.2）
- [x] Cookie の属性 → `HttpOnly; Secure; SameSite=Lax`、Better Auth が管理（05 §5.1）

### 3.3 エンドユーザー認証フロー

- [x] GPS 拒否時 → サーバー設定で `off` / `optional`（既定）/ `required`。`optional` は拒否されても継続し `location = null`、`required` は `declined`（D2, 06 §3.3）
- [x] hCaptcha 失敗時 → 結果は `captcha`。回数はレート制限に従う（IP あたり 10 回 / 10 分。05 §10.3, 03 §3）
- [x] 認証フローのセッション管理 → iron-session は廃止。FastAPI の `verification_sessions`（有効期限 10 分）と `X-Verification-Token`、Cookie は `__Host-lgf_vs`（05 §10）
- [ ] 同一 Discord ID による複数タブでの同時認証の制御（レート制限のみで、排他制御は未設計）

## 6. VPN ASN リスト

- [x] ASN ルールの UI → 組織・サーバーの許可/ブロックと実効ルールのプレビュー（02 §1.3）。1 サーバーあたり 500 件まで（01 §6）

## 9. セキュリティ

- [x] 秘密値の保存 → アプリ側で AES-256-GCM 暗号化。鍵は Key Vault から環境変数で供給（04 §6）
- [x] CSRF → Better Auth の `trustedOrigins` + Server Actions の Origin 検査（05 §1）
- [x] 入力バリデーション → Pydantic / zod（02 §3）
- [x] 監査ログ → O-04。組織・メンバー系は `POST /v1/audit-logs` で記録、保存期間は 2 年（D16, 04）
- [ ] ダッシュボードへの IP 制限・2FA の要否（Passkey は追加登録のみで、2FA としての強制はない）
- [x] SQL インジェクション → SQLAlchemy のパラメータバインディング。生 SQL は使わない
- [x] 機密データのログ出力 → IP・GPS・トークン・メールを出さない（01 §7, 06 §4）
